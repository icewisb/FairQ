# P01 goroutine 峰值专项

日期：2026-10-14。范围仅为 goroutine 计数、生命周期和限时复验；正式 60 分钟 P01 复验 **NOT_RUN / PENDING**。历史失败报告保持原样。

## 根因与证据边界

已确认负载工具的统计缺陷：原 `runtime.NumGoroutine()` 不是一致快照。在本机 Go 1.27.1 中，GC 的 `markrootFreeGStacks` 临时把已退出 goroutine 从 `sched.gFree.stack` 取走，释放栈后才放入 `sched.gFree.noStack`；`gcount(false)` 在这个窗口会把这些已退出协程算作存活。源码位于该版本 `runtime/mgcmark.go` 和 `runtime/proc.go`。

不依赖 Redis 的受控实验：先结束一批协程，用完整 goroutine profile 确认基线为 1，再只启动一个调用 `runtime.GC()` 的协程，真实存活上限为 2。预热 512 个协程时旧计数报 233，完整 profile 为 2；预热 8192 个时旧计数报 7988，profile 仍为 2，最终均为 1。十轮对照中 `NumGoroutine` 和 `GoroutineProfile(nil)` 都误报；非空单记录 profile 缓冲的十轮、144964 次采样均不超过 2。

原 P01 在 2310.179s 的单个 Worker 样本为 299，前后为 167，没有当时的调用栈。因此不能追溯证明那次增加的 132 个全部属于这一机制；其表现与已复现的统计缺陷一致。本次修复的是有直接红绿证据的采样缺陷，不将历史失败改判 PASS，也不声称已确认生产 Worker 泄漏。

## 四类现象的区分

- 正常负载：每进程 80 worker、80 handler、4 个串行维护循环，以及主程序/信号处理共 167。临时诊断增加一个采样协程，基线为 168。
- 短暂资源堆积：独立慢拨号/Context 取消探针中，80 调用槽对应最多 140 个 go-redis 后台拨号，profile 总数 222。调用停止及 Close 后仍有 140 个拨号；释放故障后约 405ms 全部退出，最终为 1。这说明在途拨号可以暂存，不足以证明永久泄漏，也不直接归因历史 299。
- 泄漏：本次没有确认 FairQ 内部的永久 goroutine 泄漏。Worker 的取消函数、timer、缓冲 result 和维护器退出路径均已核验；Handler 忽略 Context 属既定使用边界，P01 Handler 会响应取消。
- 统计误差：已退出协程被旧计数临时计入，有严格活跃上界、同步 profile 和重复实验佐证，不能通过放宽阈值处理。

## 最小修改

仅将 `tools/loadtest` 的采样替换为非空缓冲的 `runtime.GoroutineProfile`。返回的 `n` 是完整 profile 的记录数，缓冲不足时 `ok=false` 不意味着 `n` 被截断为 1；非空缓冲使本机 runtime 在计数前完成同步。每 30 秒一次采样，没有新增后台组件或生产服务。

原基线 +32、60s 后开始判断、10×80 并发、1000 Group、10万积压、Handler 1s、正式 3600s PASS 条件全部不变。Worker、Redis 配置、FIFO、Group Round Robin、Lease 和 Retry 未修改。
